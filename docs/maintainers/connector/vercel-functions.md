# local vercel node function qualification

`task go:test:integration:vercel` builds an installed-package Nitro Vercel Node
function and invokes it from an artifact-only directory. the function starts its
own packaged native connection owner using a generated workload manifest and
signed local Vercel OIDC assertions delivered through request context.

```console
mise exec node@24.20.0 -- task go:test:integration:vercel
```

the Task requires Node `24.20.0` on `PATH`, Docker, Go, Task, pnpm, and Pebble.
it never invokes mise internally. `tools/testharness` owns digest-pinned disposable
PostgreSQL; the Go fixture reuses the separated runtime's real authority/control,
two ingress processes, two relays, and native publishers. Pebble issues managed
visitor certificates through the existing DNS-01 fixture. only infrastructure
addressing and OIDC signing-key discovery use local test adapters.

Nitro `2.13.5` emits `.vercel/output` and a `nodejs24.x` function configuration.
the builder packs the SDK and matching native packages, installs those tarballs
in an independent consumer, and explicitly traces native executables, package
metadata, CommonJS entry, dependency licenses, and tnl legal files. it packages
the manifest generated by Go's `workloadmanifest.Generate` at
`.tnl/generated/workloads.json`. the builder consumer and source are deleted
before invocation. binary hashes, executable permissions, matching package
versions, legal contents, and contained symlinks are checked on both artifacts.

## invocation boundary

the local adapter imports the emitted handler unchanged. it implements the
`@vercel/request-context` symbol with per-request async storage, so the installed
`@vercel/oidc` helper reads each invocation's assertion. signed assertions travel
to the adapter over local HTTP and to native helpers over private stdin/IPC;
they are not build inputs, environment tokens, or artifact files.

each isolate starts with an empty home and temporary directory. it receives
fixture CA roots and application database authentication, without a direct
database URL or target address. `PGHOST` and `PGPORT` deliberately select an
unusable direct destination. no external connection handle, Git checkout, project
configuration, human session, or repository module path enters the function.

the check asserts:

- four concurrent cold HTTP invocations start one live owner from the packaged
  native executable; PostgreSQL has no preparation requests yet;
- concurrent HTTP and real pg queries subsequently share that same owner;
- idle background preparation refreshes the current run and its visitor token;
- with control requests held at the fixture proxy, four warm preparation pairs
  use eight direct IPC requests and zero helper processes;
- warm application traffic reaches both targets while control remains held,
  using the owner's last confirmed preparation within its existing deadline;
- assertion rotation adds one identity helper and retains the owner and session;
- another cold isolate gets its own owner and key-bound workload session;
- missing, expired, and signed wrong-project assertions fail on cold and warm
  paths without application traffic reaching either target; concurrent good and
  bad request contexts remain separate;
- real authority revocation denies the warm owner after the production
  30-second authorization bound, without a replacement session;
- both services traverse workload-authenticated ingress/relay/publisher paths,
  no human visitor device is enrolled, and function shutdown joins SDK cleanup.

the request adapter records actual helper launches, IPC operations, and live
native PIDs without replacing their implementations. the Go HTTPS front records
actual authority/control requests. a joined gate holds background preparation
during the warm checks, then resumes normal forwarding. the target
counter includes HTTP requests and PostgreSQL startup packets; publisher health
probes are excluded. full counters are retained in the invocation evidence.

body streaming, cancellation, fixed session expiry, wrong TLS identity, and
owner-death recovery stay in their existing lower-level tests. see
[native connection runtime](connection-runtime.md),
[workload sessions](../control/workload-sessions.md), and `task go:test:integration:provider-http`.

## linux function execution

the default run executes the host artifact and statically checks Linux x64.
to execute Linux x64 too, select an already-local digest-pinned Node `24.20.0`
image. the runner never pulls that image:

```console
mise exec node@24.20.0 -- task go:test:integration:vercel \
  LINUX_NODE_IMAGE=node@sha256:ba849c60be29959425b8734d57b8b4b7d56f98edd9504c9af091d5281095a71e
```

this path requires working Docker host networking between the test runner and
function containers. on Docker Desktop without host networking to macOS, run
the Task in a Linux host-network runner with the Docker socket, pinned tools,
Linux npm dependencies, and `TESTCONTAINERS_HOST_OVERRIDE=127.0.0.1`. mount a
shared temporary directory at the same absolute path in the runner and Docker
host and set `TMPDIR` to it. the function containers receive only the emitted
artifact, adapter, public fixture roots, and runtime application authentication.
their artifact mount and root filesystem are read-only; private owner files use
an empty tmpfs. PID identity includes the container's PID namespace.

the default evidence directory is `.local/vercel-function-check`; override it
with `ARTIFACTS=/absolute/path`. inspect `qualification.json`, `host-files.json`,
`linux-x64-files.json`, `host-invocation.json`, and, when selected,
`linux-x64-invocation.json`. invocation reports are written only after checks
and cleanup succeed. they contain runtime/platform, owner/helper/IPC counts,
control request budgets, and negative results, without assertions or handles.

these are local artifact/runtime results. deployed Vercel token delivery,
freeze/thaw, sandbox process limits, and platform filesystem behavior still need
deployed qualification. no Vercel account, provider API call, or deployment is
involved in this fixture.
