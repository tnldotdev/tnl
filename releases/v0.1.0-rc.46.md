## Highlights

- Hosted teams get generated `tnl.dev` suffixes. Organization members get a
  label within their team, not a global username. Saved worktree and
  deployment addresses survive restarts. A verified custom domain can move
  from a personal team to an organization without changing its delegation.
- On hosted tnl.dev, `tnl publish 3000` gets a restricted address under
  `preview.tnl.dev`. The address is saved when the publisher stops; run the
  printed command to resume it. Use `--ephemeral` to remove the service on stop
  or `naming: "opaque"` to opt new public HTTP development services into opaque
  naming. SDK temporary allocation names are unchanged.
- Run a client through a connector with `tnl connect ... -- COMMAND`. Preview
  deployment changes with `tnl apply --diff`. Shell completion includes worktree
  services and deployments, and `tnl agent-guide --skill` describes the installed
  CLI for automation.
- Publishers watch for run changes, and control can set their renewal cadence.
  Control does less PostgreSQL work during renewals and audit uploads. Relay
  drain waits for an in-flight lease renewal.
- Keepalive rediscovers a live host when saved addresses fail or a host goes
  silent before response headers. macOS client state bounds Keychain operations.

## CLI change

`tnl publish --hostname` replaces `--public-url`, and `TNL_HOSTNAME` replaces
`TNL_PUBLIC_URL`. Both a bare hostname and an `https://` origin still work:

```sh
tnl publish 3000 --hostname app.chase.tnl.hooli.xyz
```

The maintainer approved a hard rename with no aliases so the CLI matches the
`hostname` configuration field. Update scripts, environment files, and saved
restart commands before switching binaries.

## Control PostgreSQL cutover

**Do not point rc.46 at an earlier control PostgreSQL database, even if it
reports schema version 1.** The maintainer approved replacing the pre-production
PostgreSQL baseline in place to ship the new control layout, verified domain
transfers, and hosted preview allocations. There is no in-place upgrade or
automatic import for those earlier layouts.

1. Keep the old binaries, configuration, control database backup, and matching
   storage key. Keep the old database intact. Do not mix old and new server roles
   against either database.
2. Run rc.46 `tnld migrate` against a new, empty PostgreSQL database using
   `TNLD_DATABASE_DIRECT_URL`. Start matching rc.46 server roles with control
   using the new database's pooled `TNLD_DATABASE_URL`.
3. Recreate the server-side identities, teams, domains, services, and publisher
   enrollments needed in the new control database. Old control sessions and
   publisher grants do not carry over. Sign in and enroll again as needed.
4. Verify authorization, DNS, certificates, and public and connector traffic
   before moving visitors. For recovery, stop the new roles and restore the old
   roles with their matching database, configuration, and storage key. A
   binary-only rollback is not supported.

Client SQLite's schema is unchanged from rc.45; do not delete `TNL_STATE_DIR`
for this cutover. The website accounts database is separate and is not reset by
this release. Publishing the release does not perform the cutover or deploy
production.
